# Смысловая полнота и одно уточнение

ID: F003
Status: accepted
Дата: 10.11.2026
Принятие: 10.11.2026, [product-v1](../../product/accepted-decisions-2026-11-10.md). Реализация и интеграция ещё не выполнены.

## Зачем я делаю эту функцию

Я хочу показать руководителю конкретный пробел в ответе, чтобы он мог дополнить его или честно оставить неизвестное. Опираюсь на BR-05, J2, J4 и J8. Не оцениваю кандидата и не вычисляю вероятность хорошего найма.

## Что я проверяю

Я оцениваю текущий текст одной темы. F001 работает без этой оценки; голос для неё не обязателен. Соседние ответы автоматически не считаю доказательством текущей темы. Общие противоречия четырёх ответов рассматриваются в F004; здесь отмечаю найденные противоречия внутри текущего ответа.

Ограниченное уточнение подсмотрено в [исследовании аналогов](../../research/competitive-review.md). Конкретные пункты ниже я принимаю для этого прототипа; их полезность ещё требует проверки. Использую [общие правила](../shared-rules.md).

## Требования

- **F003-R1:** я возвращаю ровно один результат для каждого пункта текущей темы. У пункта есть стабильный ID, статус present, explicitly_unknown или missing и основание. Present означает конкретные сведения; explicitly_unknown — явно высказанное незнание; missing — отсутствие достаточных сведений. Неизвестное не засчитываю как present.
- **F003-R2:** длина, громкость, повторения и инструкция «поставь максимум» не повышают полноту. Для present и explicitly_unknown нужна цитата из текущего входа. Подсказка интерфейса и ответы других тем не служат доказательством.
- **F003-R3:** если есть пробел и followUpUsed=false, я могу показать один понятный уточняющий вопрос. Квота расходуется только после показа допустимого вопроса. Ошибка, отмена и отклонённый ответ сервиса её не тратят. После показа квота использована, даже если человек решил не дополнять.
- **F003-R4:** повторная оценка после правки допустима, повторное уточнение в этой теме — нет. Даже если модель прислала второе, интерфейс его не показывает. Возврат и отмена правок квоту не восстанавливают; полный сброс создаёт новую.
- **F003-R5:** полноту текущего ответа показываю отдельно от кольца: «Есть сведения: N из M; явно неизвестно: K». M равно числу пунктов темы, N — present, K — explicitly_unknown. До актуальной оценки показано «Полнота не проверена» или ожидание, без старого балла. Кольцо всегда следует F001-R6 и считает подтверждённые темы; оценка и её ошибка сами не меняют его значение. Я не называю ни один показатель процентом качества вакансии. Это уточнённое решение A10.
- **F003-R6:** правка делает старую оценку неактуальной. Новая принимается только по SH-R4 с той же версией правил. До принятия оценки пользователь видит «Полнота не проверена», а не старое значение как новое.
- **F003-R7:** я отклоняю неизвестный/повторный ID, пропущенный пункт, неверный статус, постороннюю или отсутствующую обязательную цитату. Служебную связь с запросом и версию правил задаёт приложение. Тайм-аут — 20 секунд; после ошибки доступны повтор или продолжение без оценки.
- **F003-R8:** неразрешённое противоречие сохраняю с двумя различными цитатами и затронутыми пунктами. Такой пункт получает missing с причиной конфликта. Явное самоисправление, однозначно отменяющее прежнее утверждение, считаю уточнением; сохраняю цитату с исправлением целиком. Разные условия в разные периоды не считаю конфликтом. Если связь неясна, не выбираю последнюю реплику молча. Конфликт не создаёт второе уточнение и не блокирует сводку.
- **F003-R9:** я всегда оставляю человеку решение подтвердить непустой ответ. Если сведения неизвестны, пробел остаётся после одного уточнения или проверка не работает, можно продолжить с соответствующей пометкой. Результат оценки сам не нажимает «Далее».
- **F003-R10:** я сохраняю различие обязательного, желательного и неопределённого в Q4. Если обязательность не названа, не вывожу её из одного названия инструмента. Пункт Q4.3 отражает, есть ли явное пояснение, а не устанавливает новое требование к сотруднику.
- **F003-R11:** после уточнения человек дополняет общий ответ текстом или через append из F002. Текстовое дополнение также сначала показываю отдельно и добавляю с новой строки только по нажатию, если основание не менялось. Отмена сохраняет основной текст. Повторно проверяю целый объединённый ответ; прежняя оценка не переносится автоматически. После изменения можно подтвердить допустимый текст без повторного AI-запроса с пометкой «Полнота не проверена». Лимит относится к объединённому тексту, не к каждому фрагменту отдельно.

## Мои правила оценки: rubric-v1

Это принятая версия прежней proposed-v3; при переименовании смысл пунктов не менялся. Она учитывает самоисправления, временной контекст и обязательность каждого названного требования. Старую оценку с другой версией не использую как текущую. Пункты результата задачи, вклада и обязательности — мои подсказки сверх буквальных вопросов ТЗ. Низкая оценка по ним не запрещает продолжить и не доказывает непригодность вакансии.

| ID пункта | Что считается конкретными сведениями |
| --- | --- |
| Q1.1 | Не меньше двух разных ежедневных задач с действием |
| Q1.2 | Ожидаемый результат хотя бы одной задачи |
| Q2.1 | Проект или рабочий контекст первого полугодия |
| Q2.2 | Вклад сотрудника в этот контекст |
| Q3.1 | Продолжение проекта, смена фокуса либо явное отсутствие изменений |
| Q3.2 | Конкретика следующего полугодия либо явное продолжение той же работы без изменений; простое «тот же проект» без сведений о работе ещё не закрывает пункт |
| Q4.1 | Инструмент либо явное пояснение, что выбор инструмента не принципиален |
| Q4.2 | Знание или навык, связанный с задачей |
| Q4.3 | Обязательность каждого названного инструмента/знания определена явно либо общей фразой, однозначно относящейся ко всему списку; неуказанная обязательность хотя бы одного пункта даёт missing |

Явное «не знаю» даёт explicitly_unknown для затронутых пунктов любой темы. «Пока неизвестен весь план» может относиться к обоим пунктам Q3; это два неизвестных, а не два известных факта. Одна названная задача даёт missing для Q1.1, но человек может её подтвердить с пробелом. Всего в правилах девять пунктов; на экране текущей темы их два или три.

## Данные и переходы

В запрос входят sessionId, questionId, revision, requestId, text, rubricVersion и followUpUsed. Список допустимых пунктов и их описания задаю приложением.

Ответ содержит items с slotId/status/evidence/reason, необязательный proposedFollowUp и conflicts. Полный набор items обязателен: два ID для Q1–Q3 и три для Q4, каждый ровно один раз. evidence — список дословных непустых цитат из text. Для present/explicitly_unknown он непустой; для missing обычного основания нет, а цитаты конфликта лежат отдельно в conflicts. reason не используется как новое исходное сведение.

Состояния: не проверено → проверка → оценено либо ошибка. После правки — неактуально. Сначала проверяю структуру и актуальность, потом показываю оценку и при необходимости вопрос. Наличие цитаты проверяется автоматически; подтверждает ли она смысл пункта, отдельно проверю на корпусе вручную.

## Как я проверю результат

Автоматически проверю структуру, счётчики, отмену, устаревание и квоту. На примерах C1–C14 вручную сопоставлю смысл, статусы и цитаты. Для приёмки каждый ожидаемый исход должен выполняться; запись отклонения сама по себе не означает успешный тест. Запишу модель, версии правил/промпта, параметры и результат каждого примера. Одна и та же модель не оценивает сама себя как единственный проверяющий.

## Переход к реализации

Поведение принято в product-v1. До кода использую технический план и задачи; платная обработка остаётся выключенной до проверки сервиса, обработки данных и бюджета. Проверки выше — будущие критерии, а не результаты тестов.
