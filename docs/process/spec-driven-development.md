# Spec-driven development и работа через PR

Статус: предложенный контракт процесса. Требование SDD и PR подтверждено владельцем; описанные правила конкретизируют его для проекта.

## Зачем

История проекта должна показывать, как проблема превратилась в требования, реализацию и проверенный результат. Документы создаются до соответствующего кода и меняются вместе с поведением. Спецификация — проверяемый контракт, а не ретроспективное описание уже написанного интерфейса.

Основа подхода: [GitHub Spec Kit](https://github.github.com/spec-kit/) и [SDD Quickstart](https://github.github.com/spec-kit/quickstart.html), изучены 10.11.2026. Используем последовательность specify → plan → tasks → implement → verify. Это собственный облегчённый процесс; Specify CLI не установлен и команды `/speckit-*` в проекте не запускались. Основание выбора: [ADR 0001](../decisions/0001-spec-driven-foundation.md).

## Последовательность артефактов

1. Discovery: исходная задача, первичные источники, JTBD, user flow, scope и открытые вопросы.
2. `spec.md`: пользовательская работа, требования с ID, состояния, ошибки, ограничения, критерии приёмки, нецели и нерешённые вопросы.
3. `plan.md`: архитектура, зависимости, контракты, работа с данными, варианты и способ проверки. Появляется после достаточного уточнения поведения.
4. `tasks.md`: небольшие действия со ссылками на требования и ожидаемое доказательство.
5. Реализация: отдельный PR по согласованной спецификации.
6. `verification.md`: фактические проверки конкретного commit SHA, отклонения и ограничения. Обновляется до merge.

## Статусы

| Статус | Значение | Реализация |
| --- | --- | --- |
| draft | Предложение, возможны незакрытые вопросы | Не начинать |
| ready-for-review | Автор завершил проверку полноты и вынес решения на review | Не начинать |
| accepted | Владелец принял поведение; указан источник решения и закрыты блокирующие вопросы | Разрешено планировать и реализовывать в согласованном scope |
| implemented | Код написан и проверки пройдены, доказательства приложены | Не означает публикацию или пользовательское принятие |
| superseded | Требование заменено, указана новая спецификация | Новую реализацию по старой не делать |

Автоматическая проверка документа не присваивает accepted. Решение владельца из чата допустимо как основание, если оно однозначно относится к конкретной версии поведения. Согласие на процесс SDD не является согласием на все продуктовые гипотезы.

## Правила pull request

- Небольшой PR объясняет одну цель, содержит ссылку на спецификацию и перечисляет проверенные критерии.
- Discovery, draft-спецификации, каркас приложения и функции проходят отдельными PR. Пустые PR ради количества не создаём.
- Код и его необходимая документация могут быть в одном PR реализации, но исходная спецификация уже должна быть accepted.
- Следующий PR может быть основан на ветке предыдущего, пока тот открыт. В описании явно указать зависимость; merge выполнять в порядке зависимостей с повторной проверкой после изменения base.
- До push проверить diff, отсутствие секретов и метаданные коммитов. Не переписывать опубликованную историю без причины и разрешения.
- Merge делает владелец или агент по отдельному разрешению. Деплой — отдельное действие после фактической приёмки кандидата.

Основание механики review: [GitHub: Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests). Процесс оформлен документами и шаблоном PR; защита веток и обязательное внешнее одобрение технически не настроены. Самостоятельный review автора не выдаётся за независимый.

## Definition of Ready

Названы пользователь и работа, сохранена связь с brief, определены scope и нецели, все действия и ошибки имеют исход, метрики не подменяют смысл, критерии наблюдаемы, критичные вопросы закрыты, визуальное направление выбрано для UI-реализации. Технический план не должен тайно добавлять новое поведение.

## Definition of Done

Реализация соответствует критериям, подходящие тесты и сборка проходят, затронутый пользовательский сценарий проверен, документация обновлена, ограничения названы, PR review завершён. Для голосового ввода нужны реальные микрофон и распознавание; фикстуры доказывают только поведение с фикстурами. Публикация и продуктовая приёмка отмечаются отдельно.

## Контроль изменений

Если во время реализации обнаружен конфликт, сначала обновить исходную спецификацию и назвать изменившееся требование. Существенное изменение пользовательского поведения возвращает документ на review. Мелкие технические решения внутри принятого поведения агент принимает самостоятельно и поясняет в плане/PR.
