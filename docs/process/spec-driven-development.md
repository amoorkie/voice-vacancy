# Как я работаю через спецификации и PR

Я сначала описываю нужное поведение и способ его проверки. После этого выбираю реализацию. Так в истории проекта видно, почему появилась функция и чем подтверждён результат.

Мой ориентир — [GitHub Spec Kit](https://github.github.com/spec-kit/) и его [SDD Quickstart](https://github.github.com/spec-kit/quickstart.html). Использую облегчённый процесс на Markdown и PR. Specify CLI не устанавливал, команды /speckit-* не запускал. Причины выбора сохранил в [ADR 0001](../decisions/0001-spec-driven-foundation.md).

## Какие документы я готовлю

1. Исследование, JTBD, сценарий, границы и вопросы.
2. spec.md: поведение, ошибки, ограничения и критерии.
3. plan.md: выбранный подход, сервисы, данные, ограничения и проверка.
4. tasks.md: небольшие задачи со ссылками на требования.
5. Отдельный PR реализации.
6. verification.md: фактические проверки, commit SHA и ограничения.

Техническое исследование и черновик плана могу сделать для draft: они помогают закрыть вопросы. Это не разрешает писать код функции, подключать платную обработку или выдавать поведение за принятое.

## Что означают статусы

| Статус | Как я его использую |
| --- | --- |
| draft | Я ещё уточняю поведение или ограничения; можно исследовать варианты без реализации функции |
| ready-for-review | Я проверил полноту предложения и вынес открытые решения на рассмотрение |
| accepted | Я отдельно зафиксировал принятие этой версии и основание решения; перед кодом также должен быть готов технический план |
| implemented | Код и нужные проверки выполнены с доказательствами; публикация и пользовательская приёмка отмечаются отдельно |
| superseded | Я заменил документ новой версией и дал ссылку на неё |

CI не меняет draft на accepted. Просьба исправить документы не означает принятия всех продуктовых решений. Основание принятия храню в спеке и реестре; сейчас оно отсутствует.

## Когда я перехожу к коду

До реализации я закрываю вопросы поведения, выбираю визуальное направление для UI и готовлю план. В нём должны быть проверены браузеры, форматы, провайдеры, объём данных, хранение, ограничения частоты и расходов. Решения по технологии обосновываю сам с помощью Codex; они не подменяют нужные продуктовые решения.

## Как я оформляю PR

Я оставляю одну понятную цель, ссылку на спеку, проверенные критерии и ограничения. Исследование, спеки, каркас и функции развиваю отдельными PR; пустые PR ради количества не делаю.

Зависимый PR может временно опираться на ветку предыдущего. Зависимость указываю в описании, после слияния меняю base и повторяю проверки. Опубликованную историю без отдельного решения не переписываю.

Перед push проверяю diff, секреты и метаданные коммитов. Слияние GitHub PR и деплой делаю отдельным решением. Правила review опираются на [GitHub Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests). Техническую защиту веток и обязательное внешнее одобрение пока не настраивал.

## Когда я считаю работу выполненной

Я сопоставляю код с критериями, запускаю нужные тесты и сборку, прохожу затронутый сценарий и записываю ограничения. Для голоса нужны настоящий микрофон и распознавание. Ответ-фикстура доказывает только поведение с фикстурой.

Проверку тем же Codex, который готовил изменение, называю самопроверкой. Пользовательскую приёмку, независимое ревью и публикацию не подменяю зелёным CI.

## Если требования изменились

Я сначала меняю исходное правило и объясняю, какое поведение поменяется. Существенное продуктовое изменение снова проходит рассмотрение. Обратимые технические детали внутри принятого поведения решаю при реализации и объясняю в плане или PR.
