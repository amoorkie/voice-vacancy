# Данные, API и защита расходов

Версия: api-v1. Дата: 10.11.2026. Это контракт реализации по [общим правилам](../specs/shared-rules.md), ещё не работающий сервер. Продуктовые поля и переходы определены в F001–F004; здесь я закрепляю границу между браузером, сервером и провайдером.

## Жизненный цикл данных

| Данные | Где находятся | Когда удаляются / что сохраняется |
| --- | --- | --- |
| Рабочие/подтверждённые ответы, оценки, черновик, правки | RAM вкладки | Полный подтверждённый сброс, закрытие/обновление страницы. Нет localStorage, IndexedDB, service worker cache или серверного восстановления |
| Запись и предложение расшифровки | RAM вкладки | Аудио удаляется после успешной допустимой расшифровки, ещё до выбора применения текста; также при отмене, согласованном удалении/замене, переходе и сбросе по F002-R7. При сетевой ошибке доступен ручной повтор текущей записи; после hide она не отправляется автоматически |
| Входные данные запроса и ответ провайдера | RAM сервера на время обработки | После завершения/ошибки/отмены освобождаю ссылки; не записываю файлы, тела запросов, prompts или результаты в логи |
| Аудио у OpenAI | Только запрос `/audio/transcriptions` | По текущей таблице провайдера нет хранения состояния/abuse logs. Это заявление провайдера, не проверка его инфраструктуры |
| Текст у OpenAI | `/responses`, `store=false`, без Conversations/Files/Batch | Возможны abuse logs до 30 дней и техническое кеширование по правилам провайдера. Нулевое хранение всего сценария не обещаю |
| Учёт расходов | Один локальный файл вне Git; при deploy — постоянный диск | Суммы, дата, тип операции, случайный ID/его хеш, резерв/usage и статус. Без текста, аудио, IP и связи с содержимым интервью. Итоги не сбрасываются при рестарте |
| Ограничение частоты | RAM сервера | Хеш IP с периодически меняемой солью и счётчики живут до часа. Raw IP не пишу в прикладные логи; настройки логов хостинга проверяю до deploy |
| Экспорт | Файл, скачанный человеком | Уже контролируется человеком; сброс вкладки не удаляет скачанный файл |

Детали внешнего хранения и доступности приведены с источниками в [выборе сервисов](services-and-budget.md). Технический счётчик расходов не является историей ответов и не добавляет БД пользователей.

Перед первой внешней обработкой показываю короткое объяснение: запись или текст уйдут OpenAI для выбранного действия; ответа не будет в истории приложения после закрытия, но текст может храниться у провайдера по его правилам. Подробности доступны по ссылке. Отправка начинается только по явному действию. Отказ оставляет текстовый ввод и экспорт. Не прошу реальные персональные сведения кандидатов: продукт описывает роль.

## Общие правила маршрутов

Все три POST работают с того же origin по HTTPS; локально допустим localhost. В разработке Vite проксирует `/api` на loopback Fastify. Ключ только в серверной переменной, публичный URL провайдера фиксирован конфигурацией, пользователь не может передать свой endpoint или модель. Секреты не имеют префикса `VITE_`.

Сервер выдаёт короткоживущий подписанный demo-token без аккаунта; клиент хранит его в памяти. Токен нужен для ограничения попыток, не доказывает личность человека. Проверяю Origin, тип запроса, подпись и срок токена, заголовок приложения; CORS не разрешает сторонние сайты. Это снижает случайное использование endpoint, но не мешает целенаправленному посетителю получить свой токен. Финансовая граница — общий серверный бюджет.

Все входы строго проверяются по схеме с запретом лишних полей. Версии промпта, модели и рубрики выбирает сервер. `requestId` имеет ограниченный UUID-формат; sessionId не является секретом или правом на чужие данные. Идентификаторы из модели игнорируются: сервер добавляет исходный envelope сам. Повтор того же requestId не вызывает провайдера второй раз; возвращаю `duplicate-request`. Настоящий ручной повтор имеет новый ID.

| Маршрут | Вход | Успешный выход |
| --- | --- | --- |
| `POST /api/transcriptions` | Multipart: один WebM-файл, sessionId, requestId, questionId, revision, intent replace/append | `text` и исходный envelope; язык `ru`, никакого изменения редактора сервером |
| `POST /api/completeness` | JSON: sessionId/requestId/questionId/revision, полный текущий text | items/conflicts/proposedFollowUp по F003 + исходный envelope, rubricVersion и promptVersion |
| `POST /api/vacancy` | JSON: sessionId/requestId/snapshotId/draftEditRevision и ровно четыре подтверждённых ответа Q1–Q4 | `kind=draft` с шестью разделами либо `insufficient-input`; envelope и promptVersion по F004 |

На границе провайдера application IDs не передаю без нужды. Модели проверки достаточно текста одной темы и фиксированной рубрики, генерации — четырёх ответов с короткими метками источников. Заново проверяю связи с исходным запросом на сервере, затем актуальность на клиенте. Подтверждение пользователем возможно только в интерфейсе; модель его не выставляет.

## Размеры, длительность и тайм-ауты

| Проверка | Правило |
| --- | --- |
| Рабочий ответ | 1–6000 Unicode code points, не пустой после trim; исходный текст не сокращаю |
| Multipart | Только один файл; файл >0 и ≤10 485 760 байт; суммарное тело с метаданными ≤11 MiB; ограничено число/длина полей |
| Запись | MediaRecorder сначала проверяет `audio/webm;codecs=opus`, затем `audio/webm`. Если ни один формат не поддержан, доступен текст; другие контейнеры пока не заявлены |
| Проверка медиа на сервере | MIME и расширения недостаточно: ограниченный по памяти/времени ffprobe через stdin, без shell и временного файла, проверяет WebM/Opus, одну аудиодорожку, отсутствие видео и длительность по пакетам. Не доверяю duration, присланной браузером. Нет достоверной длительности или >122 секунд — не отправляю платный запрос. Допуск 2 секунды нужен для финальных пакетов после остановки на 120; он не продлевает таймер интерфейса |
| JSON | Тело до 160 KiB; полный upstream-вход вместе с инструкциями/схемой: проверка ≤48 KiB UTF-8, генерация ≤128 KiB UTF-8. Экранирование включено; никаких тихих усечений |
| Лимит ответа модели | Проверка `max_output_tokens=8192`; генерация `65536`. Это потолок расходов, не цель длины. Сгенерированные текстовые значения суммарно ≤12000 code points, включая evidence, reasons, неизвестное и конфликты; машинные ID/enum не являются пользовательским текстом |
| Ожидание | Клиент: ASR 45, проверка 20, генерация 60 секунд с начала отправки. Сервер отменяет upstream по disconnect/deadline; свой потолок ожидания после получения тела 40/18/55 секунд. Upload тоже ограничен; общий клиентский срок остаётся главным правилом применимости |

Для packet-probe нужны ограничения времени 3 секунды, вывода 4 MiB и корректная обработка kill/error; вывод не логирую. Использую только контейнер WebM и протокол pipe, без доступа к произвольным URL/файлам. Длительность сверяю по пакетам и их временным меткам; неверные/немонотонные значения отклоняю. Возможности `show_packets`, `show_streams` и JSON описаны в [официальной документации ffprobe](https://www.ffmpeg.org/ffprobe.html). В каркасе закрепляю поддерживаемую версию FFmpeg/ffprobe из официального дистрибутива. Это единственная отдельная системная утилита; транскодирование и файловое хранилище не нужны. При тесте проверю реальный WebM Chrome/Edge: у него может отсутствовать общий duration, поэтому одного чтения заголовка недостаточно. Если probe не справляется, интеграцию не объявляю готовой и исправляю адаптер до включения.

Окно Luna 1 050 000 токенов и максимум выхода 128 000 по [модели](https://developers.openai.com/api/docs/models/gpt-6-luna) больше наших пределов. Точный сериализованный запрос проверяю токенизатором, совместимым с выбранной моделью, в T02/T09. Если такого локального токенизатора нет, использую консервативную верхнюю оценку UTF-8 bytes плюс служебный запас и проверяю её контрольным подсчётом до включения. Входные лимиты не подменяю средней длиной русских слов. Автоматическое усечение контекста отключаю.

## Ответы и ошибки

Единый безопасный ответ ошибки: `code`, понятное `message`, `requestId`, `retryable`. Стек, ключ, исходный prompt и тело ошибки провайдера наружу не попадают.

| HTTP / code | Что делает интерфейс |
| --- | --- |
| 400 invalid-input / unsupported-audio | Сохраняет текст, объясняет исправление или предлагает новый ввод |
| 413 input-too-large | Показывает предел; ничего не обрезает и не отправляет повторно |
| 409 duplicate-request | Не запускает вторую обработку, сохраняет данные |
| 429 rate-limited / budget-exhausted | Сохраняет работу; при rate-limit показывает время повтора, при бюджете — текстовый путь/экспорт |
| 503 integration-disabled / provider-unavailable | Не выдаёт фикстуру за результат; текстовый сценарий доступен |
| 502 invalid-provider-output / provider-refusal | Не применяет частичный ответ; предлагает ручной повтор или выход со сводкой |
| 504 timeout | Попытка неактивна; поздний результат игнорируется |

`insufficient-input` — допустимый бизнес-результат 200, а не сбой сети. Он никогда не удаляет прежний черновик. Отмена ожидания тоже сохраняет уже введённое. Сырые данные показываю как текст, без HTML/Markdown-инъекций; ограничения длины применяются и к ответам провайдера.

## Семантика и генерация

Промпты и JSON Schema версионирую в Git. Входной ответ — цитируемые данные, любые инструкции внутри него не могут менять рубрику, требовать tools или выбирать endpoint. Никаких вызовов инструментов у модели нет.

F003: обязательны все slotId текущей темы, допустимый статус и точные цитаты. Два разных свидетельства конфликта, явные самоисправления и различие полугодий обрабатываются как в спеке. Квоту уточнений ведёт клиентский домен; модель может предложить вопрос, но не управляет квотой.

F004: проверяю шесть разделов, тип каждого item, уникальные ID, questionId/confirmedRevision и точную цитату. Неподтверждённые факты нельзя спрятать в reason/clarifications. Валидная схема и совпавшая цитата не доказывают, что утверждение следует из неё: это отдельная проверка качества по корпусу. Ручная правка снимает машинное доказательство изменённого раздела и не меняет исходный generated-вариант.

## Ограничения нагрузки и бюджета

Начальные серверные пределы: не более 6 внешних попыток в минуту и 40 в час на demo-token; 120 в час на хеш IP; максимум 3 внешние операции глобально. На token одновременно максимум одна операция каждого типа. Выдача токена ограничена 10 в час на хеш IP. Ответ 429 не расходует платный запрос; клиент не обходит предел новым token автоматически. Внутренние перезапуски страницы не сбрасывают глобальный бюджет.

Счётчик расходов использую только в одном процессе. Все резервы сериализуются, записываются атомарно с синхронизацией на диск **до** upstream-вызова. При параллельных запросах остаток проверяется внутри этой операции. После ответа сверяю фактические usage/длительность и отпускаю только доказанный остаток. Незавершённые запросы после рестарта остаются учтёнными по полному резерву. Если диск недоступен, счётчик повреждён или второй процесс пытается его открыть, AI выключается.

Проверяю границы лимита, гонку последних двух резервов, отмену после отправки, повтор ID, рестарт и ошибку записи. Общая сумма/дневной лимит не могут превышаться за счёт параллельности. Ограничение считает расходы только нашего сервера: ключ выделенного проекта не использую в сторонних задачах. Выход за пределы тарифа или реальное списание выше резерва отключает последующие вызовы до сверки.

Анонимное публичное демо можно намеренно довести до лимита; это ограничение первой версии. Оно остановит AI для всех, сохранив текстовый сценарий. Для большого публичного запуска потребуется отдельное решение о защите доступа и инфраструктуре. Для небольшого демонстрационного проекта не добавляю аккаунты заранее.

## Проверка до включения

1. Подтверждены доступность аккаунта, модели, оплата и страны использования.
2. Согласованы сумма расходов и понятное объяснение обработки данных; ключ передан через защищённую настройку, не чат/Git.
3. Пройдены локальные проверки схем, медиа, отключённого режима, бюджета, rate-limit, timeout и отсутствия секретов в клиентской сборке.
4. Начальный AI-корпус использует только вымышленные тексты и специально записанное тестовое аудио; включение ограничено этими проверками.
5. После реальных тестов записаны качество/задержки/usage. Публичное демо включается отдельно после проверки HTTPS, постоянного счётчика, логов хостинга и лимитов трафика.

Пункты ещё не выполнены; этот документ делает предстоящее подключение проверяемым и позволяет разрабатывать локальные части заранее.
